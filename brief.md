# Test automation project for Todoist

## Goal

- automation goal - quick feedback, help regression testing
- for business, the key functionality is working with tasks
- requirements and acceptance criteria - we don't have them; the test cases (with steps and expected results) are the contract

## Scope

- use the test cases provided by testers in `Test Cases for automation.md`
- we are not going to automate sections because they are going to change in the next release
- TC-010 is dropped (it depends on sections)
- the account is a free Todoist account - features that need a paid plan are out of scope

## Test cases

- test case steps and expected results are written by the test owner (me); Claude may draft them, but the owner approves them before any automation code is written
- test case name contains the test id in the tag and in the title, e.g. tag `@TC-002`, title `TC-002 A new task is created with the text that was entered`
- organize test cases into test suites, use tags (smoke, regression, e2e, negative)
- tag mapping - smoke is a subset of regression:
  - wave 1 (TC-001..005) - `@smoke @regression`
  - waves 2 and 4 (TC-006..009, TC-012..013) - `@regression`
  - wave 3 (TC-011) - `@e2e @regression`
  - wave 5 (TC-014..015) - `@negative @regression`
- the hourly run executes `@smoke`, the PR run executes `@regression`
- use test design techniques (equivalence partitioning, boundary values) and one behaviour per test

## Tools and code

- tools - playwright with typescript, API testing via `APIRequestContext` (no browser)
- endpoints - https://developer.todoist.com/api/v1/ ; the contract is https://developer.todoist.com/openapi.json
- project structure - object oriented API clients (one per resource: projects, tasks, labels, comments), tests do not call endpoints directly, test data kept separate from tests
- use eslint for static analysis (typescript-eslint + eslint-plugin-playwright)
- use prettier
- use a local git hook (husky) to block direct commits to main - this is a convenience only; real protection is the GitHub ruleset below

## Environments and security

- environments - currently just production; configuration is limited to base URL + token per environment, no speculative dev/test setup
- security - use secrets manager - github action secrets, `.env` file (gitignored), `.env.example` committed
- the access token must never appear in logs, reports or traces - mask the `Authorization` header

## Test data

- test data is generated by every test and cleaned up afterwards
- all test data names carry a unique run prefix (e.g. `autotest-<runId>-`)
- a cleanup sweep deletes leftovers by prefix before and after each run, so a failed teardown cannot block later runs (free plan project limit)
- run with 1 worker - all runs share one account

## Pipelines and reporting

- use github actions, run tests with every PR, smoke tests every hour (scheduled on main)
- PRs must come from branches in this repo, not forks (forks do not receive secrets)
- reporting - playwright html report stored in github actions pipeline artifacts
- traces - only on failure (`retain-on-failure`), stored in pipeline artifacts, artifact retention 7 days
- failures of the hourly smoke run are notified to me (the person who last edited the schedule in the workflow)
- time budget - smoke run under 2 minutes, full PR run under 10 minutes
- retries - 1 retry in CI, 0 locally; a test that passes only on retry is flaky and gets an issue to fix it

## Workflow

- every change should create an issue > branch > PR
- commit messages - include issue id, brief summary of changes
- main is protected by a GitHub ruleset: no direct pushes, PR with 1 approval required
- every PR is reviewed by business; the PR description lists the covered test cases in plain language (id, name, steps, expected result) so it can be reviewed without reading code
- PRs are merged by me (test owner) after business approval and green CI
- every time you finish creating a PR, give me the url to PR and a brief summary of changes
